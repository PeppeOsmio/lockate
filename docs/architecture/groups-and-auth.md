# Groups and authentication

[← Architecture](../architecture.md)

## Entities

| Entity | Stores |
|---|---|
| `AnonymousGroup` | Id, encrypted name. |
| `AGMember` | Id, group, encrypted name, admin flag, SHA-256 of its token, push registration. |
| `AGMemberLocation` | A member's saved position: encrypted coordinates and activity, IVs, time. |
| `AGPlace` | A group's place: encrypted centre, radius and name ([Places](places.md)). |

There are no user accounts: a person is a member of each group separately, with a different id,
name and token in each. Members join only through invites ([Invites](invites.md)).

## Member tokens

A member authenticates with a 32-byte random token generated by the app, sent as
`Authorization: AGMember {memberId} {token}`. The server stores `SHA-256(token)` and compares in
constant time (`MessageDigest.isEqual`). On every `@SecuredAGMember` endpoint
`AGMemberAuthInterceptor` checks it through `AGMemberAuthenticator` and puts the resulting
`AGMemberAuthentication` in the security context, where the controller gets it as a parameter. Every request checks the database, so a removed member
fails at once; there is no cache.

**Why SHA-256 and not BCrypt.** BCrypt's slowness protects guessable passwords, and costs
50–100 ms of CPU per check: fine once per socket, too much for a post every 2 s per moving member.
A 256-bit random token can't be guessed with any hash, so SHA-256 is as safe and costs
microseconds. The invite join tokens use SHA-256 too. Switching deleted every existing group,
since BCrypt hashes can't be converted without the tokens.

## Client-generated ids

Group, member and place ids, and push registration ids, are generated by the app, because they
are part of the AAD of the fields that belong to them ([Encryption](encryption.md)). An accidental
collision of random UUIDs is negligible, so the app doesn't retry. A deliberate one is the real
case, and the server never overwrites what belongs to someone else: a taken group or member id is
a 409 (`AGIdTakenException`), a place id of another group a 409 (`place_id_taken`), and a push
registration is keyed by the authenticated member.

## Server access: API keys and admin

- **API keys** (`X-API-KEY`): with `REQUIRE_API_KEY=true` the server accepts only clients that
  present a key (`ApiKeyAuthFilter`), so a self-hoster can keep strangers off their server. The app
  asks for it with the server URL. A key is `{id}:{secret}`; the server keeps the SHA-256 of the
  secret, compared in constant time, an optional label set by the admin and an optional expiry,
  from which the key is refused like a wrong one. When a key was last used is written at most every
  10 minutes, so checking a key isn't a database write on every request. The filter leaves
  `/api/v1/admin/**` alone: the admin key comes in the same header and is checked there.
- **Admin** (`X-API-KEY` = `ADMIN_API_KEY`, `@SecuredAdmin`): the admin API and the admin UI on top
  of it manage groups, members and API keys. → [Administration](admin.md)

## Retention

A member's positions are relayed every time and kept in Redis as its last position
(`ag-location:{groupId}:{memberId}`, for the retention), which snapshots give at once. The member
goes into the set `ag-unsaved-locations`, and `LocationSaveJob` saves the last position of each
member in it every 2 minutes (`lockate.retention.anonymous-group.location.save-interval`): it pops
the whole set, so with several backend instances each member is saved by one of them, and the last
position of a burst (the switch to still right after moving) is always saved, at most 2 minutes
late. A member who leaves loses its key. The
`LocationRetentionJob` deletes saved positions older than 7 days
(`…location.duration`, daily `…location.cron`). The saved record is only there so a member who
opens the map sees where the others last were. Each job, once its transaction commits, keeps when
it ran and how many positions it saved or deleted in Redis (`JobRunService`, `job-run:{job}`), so
the [admin overview](admin.md) can tell a job that stopped running.
